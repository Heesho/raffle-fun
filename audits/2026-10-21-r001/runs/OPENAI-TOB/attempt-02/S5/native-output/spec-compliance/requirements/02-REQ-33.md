## REQ-33 — Roll back failed redemption

> "must revert all effects on delivery failure."
> — target/DESIGN.md:L2

The surrounding sentence is:

> "Settlement is permissionless, storage-only; redemption requires current ticket owner, burns claim atomically, and must revert all effects on delivery failure."
> — target/DESIGN.md:L2

The API states:

> "Any failed delivery reverts the burn and every redemption state change."
> — target/packages/contracts/src/interfaces/IRaffle.sol:L335

**Verdict:** implemented · confidence: high

---

**What this demands of an implementation:** A failed NFT or cash delivery must leave no committed effects from that redemption: the ticket burn, redemption flags, payout accounting, events, and any settlement performed inside the same call must roll back. The two delivery branches and their preceding writes are in `target/packages/contracts/src/Raffle.sol:L309-L345`; inline settlement writes are in `target/packages/contracts/src/Raffle.sol:L533-L557`. Settlement committed in an earlier transaction is outside the effects of the failed redemption; the separate entrypoint is `target/packages/contracts/src/Raffle.sol:L304-L306`.

The NFT calls are ordinary external interface calls with no exception handler. A revert from either `transferFrom` or `ownerOf` therefore propagates; a returned owner other than the winner explicitly reverts. The cash branch calls `_transferQuote`, which rejects protocol destinations and invokes the reverting SafeERC20 operation (`target/packages/contracts/src/Raffle.sol:L334-L342,L564-L567`).

```solidity
// target/packages/contracts/node_modules/@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol:L33-L37
function safeTransfer(IERC20 token, address to, uint256 value) internal {
    if (!_safeTransfer(token, to, value, true)) {
        revert SafeERC20FailedOperation(address(token));
    }
}
```

The actual low-level transfer helper was read: `_safeTransfer` calls the token at L184, bubbles failed calls with `revert` at L189-L191, and otherwise accepts a return word of one or a successful empty response from a contract at L187-L196. A false return reaches the explicit `SafeERC20FailedOperation` above. The `bubble` argument is **true** on this path; the non-reverting `trySafeTransfer` variant is a different function (`target/packages/contracts/node_modules/@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol:L33-L37,L52-L54,L176-L200`).

Applying EVM revert semantics to these uncaught failure paths rolls back the entire redemption call, including earlier writes and logs and changes made by nested calls. No compensating write or best-effort recovery substitutes for rollback (`target/packages/contracts/src/Raffle.sol:L309-L345,L564-L567`; `target/packages/contracts/node_modules/@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol:L33-L37,L176-L200`).

**Paths walked:**

- **Entry and existing settlement:** `redeemWinningTicket` rejects already redeemed or non-winning outcomes, verifies the settled ticket ID when settlement already exists, and checks the current owner. `ownerOf` reaches `_requireOwned` and the `_owners` lookup, reverting for a nonexistent ticket. These failures do not proceed to delivery (`target/packages/contracts/src/Raffle.sol:L309-L321`; `target/packages/contracts/node_modules/@openzeppelin/contracts/token/ERC721/ERC721.sol:L61-L63,L146-L148,L426-L432`).

- **Inline settlement:** When `settlementComplete` is false, redemption calls `_settleWinningTicket` before the owner check and burn. The helper validates the terminal status and inclusive winning range, computes allocations, and writes `winnerProceeds` for cash, `settlementComplete`, `winningTicketId`, `unsettledPot`, `sponsorProceeds`, and `protocolFees`, then emits `WinningTicketSettled`. A later delivery failure unwinds all of these same-call effects (`target/packages/contracts/src/Raffle.sol:L314-L315,L451-L455,L533-L557,L579-L585`). The called `Math.mulDiv` and its `mul512`, `ternary`, boolean cast, and panic helper were read; they contain arithmetic or reverting error paths, not an external settlement boundary (`target/packages/contracts/node_modules/@openzeppelin/contracts/utils/math/Math.sol:L37-L46,L143-L150,L206-L277`; `target/packages/contracts/node_modules/@openzeppelin/contracts/utils/math/SafeCast.sol:L1157-L1161`; `target/packages/contracts/node_modules/@openzeppelin/contracts/utils/Panic.sol:L50-L55`).

- **Ticket burn:** `_burn` calls `_update` with both recipient and authorization set to zero. Raffle's override skips its destination check for this zero-address burn and calls the base implementation. The base clears token approval, decrements the owner's ticket balance, sets ownership to zero, and emits `Transfer`; its authorization check and recipient balance increment are not taken on this burn path. The approval helper receives `emitEvent=false` and `auth=0`, so its owner/authorization branch is also skipped. These are storage/log effects within the redemption call and are undone on delivery failure (`target/packages/contracts/src/Raffle.sol:L325,L497-L502`; `target/packages/contracts/node_modules/@openzeppelin/contracts/token/ERC721/ERC721.sol:L216-L245,L303-L308,L383-L399`).

- **NFT delivery, with either prior or inline settlement:** `PrizeAlreadyClaimed`, a reverting transfer, a reverting ownership query, or an ownership mismatch all abort redemption. There is no catch-and-continue branch; `WinningTicketRedeemed` is emitted only after the delivery branch completes (`target/packages/contracts/src/Raffle.sol:L329-L345`). This covers a transfer that returns normally without moving the NFT when `ownerOf` continues to report the previous owner (`target/packages/contracts/src/Raffle.sol:L334-L336`).

- **Cash delivery, with either prior or inline settlement:** Zero proceeds revert. Otherwise the claim is cleared before `_transferQuote`, whose destination screening checks direct protocol addresses and, for other addresses with code, the factory registry. A rejected destination or failing factory query aborts the same call; allowed destinations reach SafeERC20. Token reverts propagate, and a false transfer response becomes a revert, restoring the cleared proceeds and burned ticket (`target/packages/contracts/src/Raffle.sol:L338-L342,L564-L567,L593-L605`; factory getters at `target/packages/contracts/src/RaffleFactory.sol:L41-L42,L53-L54`; `target/packages/contracts/node_modules/@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol:L33-L37,L176-L200`). A normal successful transfer is not a delivery-failure path. The applicable dependency assumption is quoted explicitly: "Quote token and Chainlink wrapper are trusted canonical dependencies" (`target/DESIGN.md:L2`), and "canonical USDC trust model assumes standard, non-rebasing, fee-free transfer semantics." (`target/packages/contracts/src/Raffle.sol:L561`).

- **Modifier:** `nonReentrant` invokes its pre-check, the function body, and its post-write without any exception handler. Its helpers reject the entered state and use a storage-slot reference for the entered/not-entered writes. It neither catches a delivery failure nor converts one into success (`target/packages/contracts/src/Raffle.sol:L309`; `target/packages/contracts/node_modules/@openzeppelin/contracts/utils/ReentrancyGuard.sol:L69-L73,L88-L118`; `target/packages/contracts/node_modules/@openzeppelin/contracts/utils/StorageSlot.sol:L93-L97`).

- **Clone entry:** The factory creates the raffle using `Clones.clone(raffleImplementation)`. The selected overload installs the delegatecall runtime whose suffix `5af43d82803e903d91602b57fd5bf3` copies returndata and branches to `REVERT` on failed delegatecall or `RETURN` on success. Thus a failed implementation call is also a failed clone call (`target/packages/contracts/src/RaffleFactory.sol:L105-L106`; `target/packages/contracts/node_modules/@openzeppelin/contracts/proxy/Clones.sol:L32-L34,L47-L61`). This is a static reading of the source bytecode literal, not an execution result.

---

**How the verdict was reached:** Implemented: both delivery alternatives propagate failure to the redemption boundary, and the inherited burn and optional settlement execute within that same reverting call. NFT ownership mismatch has an explicit revert; ERC20 false returns have an explicit revert in the wrapper; external-call reverts are not swallowed. These are concrete enforcement paths, not conclusions from method names (`target/packages/contracts/src/Raffle.sol:L309-L345,L533-L567`; `target/packages/contracts/node_modules/@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol:L33-L37,L176-L200`). There is no identified delivery-failure path that commits only part of redemption, so `partial` is not supported. The checks implement the quoted atomicity requirement rather than an additional restriction warranting `stronger-than-spec`.
