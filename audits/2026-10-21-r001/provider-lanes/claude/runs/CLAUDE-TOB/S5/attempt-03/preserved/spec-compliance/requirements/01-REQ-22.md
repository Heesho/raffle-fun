## REQ-22 — Rounding remainder allocated without loss

> "remainder must be allocated without loss"
> — DESIGN.md line 2, sentence 8. Full sentence: "Rounding is floor on aggregate protocol fee; remainder must be allocated without loss."

**Verdict:** implemented · confidence: high

---

**What this demands of an implementation:** in every terminal outcome, the quote-token amounts assigned to parties
must sum exactly to the gross pot. No unit truncated by rounding may be left unassigned or unclaimable. The outcomes
come from the same DESIGN.md line:

- "Reserve met awards NFT and 95% sponsor / 5% treasury." → sponsor + treasury = gross; winner cash = 0
- "Reserve missed awards 80% gross to winner, 15% sponsor, 5% treasury." → winner + sponsor + treasury = gross
- "Refund outcome pays 100% per entry and returns prize." → total refunds = gross

The gross pot is `unsettledPot` (Raffle.sol:L91). The document does not say which party receives a remainder.

---

**Where enforcement lives:**

```solidity
// Raffle.sol:L539-L555  (_settleWinningTicket)
uint256 grossPot = unsettledPot;
uint256 protocolFee = Math.mulDiv(grossPot, RaffleConstants.PROTOCOL_FEE_BPS, RaffleConstants.BPS);
uint256 sponsorAmount;

if (result == Status.NftWon) {
    sponsorAmount = grossPot - protocolFee;
} else {
    cashAmount = Math.mulDiv(grossPot, RaffleConstants.CASH_WINNER_BPS, RaffleConstants.BPS);
    sponsorAmount = grossPot - protocolFee - cashAmount;
    winnerProceeds = cashAmount;
}

settlementComplete = true;
winningTicketId = ticketId;
unsettledPot = 0;
sponsorProceeds = sponsorAmount;
protocolFees = protocolFee;
```

- The sponsor share is not its own percentage. It is computed by subtraction, so `protocolFee + sponsorAmount == grossPot`
  (NftWon) and `protocolFee + cashAmount + sponsorAmount == grossPot` (CashWon) hold for every `grossPot`. Anything
  the floors at L540/L546 truncate goes to `sponsorAmount`. The NatSpec records the same choice at Raffle.sol:L529-L530,
  RaffleConstants.sol:L7-L8, IRaffle.sol:L121 and IRaffle.sol:L328.
- The three-argument `Math.mulDiv` computes "floor(x * y / denominator)" (Math.sol:L200, L206).
- L544 and L547 are checked subtractions (pragma 0.8.36, no `unchecked` anywhere in src). They cannot underflow,
  because floor(g·500/10000) + floor(g·8000/10000) ≤ 0.85·g.
- On the NftWon branch `winnerProceeds` is never written. Its only other write is L341 (`= 0`), so winner cash is 0.
- L553 zeroes `unsettledPot` in the same frame that writes all three buckets, so no part of the pot stays unallocated.

```solidity
// Raffle.sol:L296-L298  (enableRefunds)
uint256 liability = unsettledPot;
unsettledPot = 0;
remainingRefundLiability = liability;

// Raffle.sol:L362-L368  (refundTickets)

amount = aggregateEntries * ENTRY_PRICE;
```

- The refund path has no division, so nothing is rounded. Each ticket refunds entryCount × ENTRY_PRICE, the same product
  that was added to the pot when the ticket was bought (L223, L233).

**Arithmetic, recorded once.** `unsettledPot` has three writers. L233 adds `grossAmount`, where
`grossAmount = uint256(entryCount) * ENTRY_PRICE` (L223); L297 and L553 set it to 0. So whenever it is allocated,
grossPot = n × 1,000,000, with n = `totalEntries`. The constants are `BPS = 10_000`, `PROTOCOL_FEE_BPS = 500`,
`CASH_WINNER_BPS = 8000` and `ENTRY_PRICE = 1_000_000` (RaffleConstants.sol:L12, L15, L18, L21):

| outcome | treasury | winner | sponsor (residual) | sum |
|---|---|---|---|---|
| NftWon | n × 50,000 (5%) | 0 | n × 950,000 (95%) | n × 1,000,000 |
| CashWon | n × 50,000 (5%) | n × 800,000 (80%) | n × 150,000 (15%) | n × 1,000,000 |

Both 1,000,000 × 500 / 10,000 and 1,000,000 × 8,000 / 10,000 are exact integers, so the floor at L540/L546 truncates
nothing on any reachable input. The sums are exact because of the residual construction, which would also hold if
the pot were not a whole multiple.

**How the verdict was reached:**

- **Not `partial`:** there are exactly three outcomes, and each was walked. No path allocates part of the pot and
  leaves the rest: L553 and L297 zero `unsettledPot` in the same frame that assigns the full amount elsewhere.
- **Not `stronger-than-spec`:** the document asks for lossless allocation and leaves the recipient open. The code
  makes that choice (the sponsor) rather than adding a constraint. Remainders are structurally zero, but that follows
  from the documented entry price and rates, not from an extra check.
- **Meaning of "remainder":** it can mean the rounding dust or the post-fee balance. The sums equal grossPot under
  either reading, so the verdict does not depend on which is meant.

A related divergence that does not affect this requirement: the design names floor rounding only for the "aggregate
protocol fee". The code also floors the 80% winner share (L546) and sends any dust to the sponsor (IRaffle.sol:L328).
That is a choice of who receives the remainder, which this requirement leaves open. On reachable pots it truncates
nothing.

**Open questions:**

- *Outside this requirement; for the payout-destination requirement.* The sponsor bucket, which would hold any
  remainder, can only be claimed if `sponsorRecipient` can be paid.
  - Screening at initialisation (Raffle.sol:L193) calls `isRaffle` only for addresses that already have code (L602).
  - Clones are deployed with CREATE (RaffleFactory.sol:L106 → Clones.sol:L32-L33, L57), so their addresses can be
    predicted.
  - A `sponsorRecipient` set to a future clone's address would therefore pass at creation (also RaffleFactory.sol:L166).
    Once that clone is registered, `_transferQuote` would reject it at L565.
  - This would strand the whole sponsor share, not a rounding remainder, and it requires the sponsor to choose that
    recipient.
- The equality "allocations = gross" holds between internal ledger values. It equals the tokens actually received only
  under the documented trust model: "Quote token and Chainlink wrapper are trusted canonical dependencies" (DESIGN.md),
  and "standard, non-rebasing, fee-free transfers" (IRaffle.sol:L13-L14). Token behaviour was not evaluated.
