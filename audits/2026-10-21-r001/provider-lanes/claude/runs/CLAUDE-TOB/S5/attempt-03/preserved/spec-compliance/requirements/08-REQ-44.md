## REQ-44 — transaction decisions reread current chain state

> "transaction decisions must reread current chain state"
> — DESIGN.md line 2, sentence 17. Full sentence: "Frontend discovery is advisory; transaction decisions must reread current chain state."

**Verdict:** implemented · confidence: medium

**Scope:** this verdict covers only the on-chain half. The client half has no code anywhere in the provided tree, so it was not checked (see Searched).

---

**What this demands of an implementation:** The sentence is aimed at clients. A transaction a frontend builds must come from a fresh read of contract state, not from discovery data such as an indexer, the event log, or a cached listing. The Holds-if splits the requirement in two:

1. *Client half*: "transactions are built from freshly read contract state." This is not checkable here, because no client code exists.
2. *On-chain half*: "on-chain each function decides from current storage and ownership at execution time." For these contracts that means four things:
   - (a) No state-changing function takes a caller's claim about chain state as authoritative, whether that claim is an owner, an amount owed, which ticket won, or a fee. Caller-supplied identifiers are re-verified against storage.
   - (b) Ownership comes from a live `ownerOf` in the executing transaction, never from an address recorded in an earlier one.
   - (c) Prices and fees are read at execution, not taken from a stored or caller-quoted value.
   - (d) No local or stored copy of state is used after something could have changed it.

---

**Where enforcement lives:**

**Ownership is read live, every time it is used.**

```solidity
// Raffle.sol:L320-L321  (redeemWinningTicket)
address winner = ownerOf(ticketId);
if (msg.sender != winner) revert NotTicketOwner(ticketId, msg.sender, winner);

// Raffle.sol:L357-L364  (refundTickets)
for (uint256 index; index < ticketQuantity; ++index) {
    uint256 ticketId = ticketIds[index];
    address owner = ownerOf(ticketId);
    if (msg.sender != owner) revert NotTicketOwner(ticketId, msg.sender, owner);
    (uint128 firstEntry, uint128 lastEntry) = ticketRange(ticketId);
    aggregateEntries += uint256(lastEntry) - uint256(firstEntry) + 1;
    _burn(ticketId);
}
```
- **No override.** `ownerOf` is not overridden in `src`. It resolves to OZ `ERC721.sol:L61-L63` → `_requireOwned` (`L426-L432`) → `_ownerOf` → `_owners[tokenId]` (`L146-L148`), which reverts for burned or unminted IDs.
- **The refund loop rereads on every iteration.** Each read comes after the previous iteration's `_burn` has zeroed `_owners` (`ERC721.sol:L304` → `L240`). A duplicate ID therefore reverts on its second read, which matches `IRaffle.sol:L341`: "Duplicate, nonexistent, or foreign-owned IDs revert the entire batch."
- **The stored winner address is never used to decide.** `winnerRecipient` is the only stored "winner" address. It is written at `Raffle.sol:L323`, after the live read, and nothing in `src` reads it.
- **Ticket transfers authorize against current state.** OZ `_update` reads `_ownerOf` at `L217` and checks `auth` against current approvals at `L220-L222` (`_isAuthorized`, `L164-L168`).

**Caller-supplied identifiers are re-verified against storage.** This is the on-chain side of "Frontend discovery is advisory".

```solidity
// Raffle.sol:L579-L585
function _requireWinningTicket(uint256 ticketId) private view {
    (uint128 firstEntry, uint128 lastEntry) = ticketRange(ticketId);
    uint128 selectedEntry = winningEntry;
    if (selectedEntry < firstEntry || selectedEntry > lastEntry) {
        revert TicketDoesNotContainWinningEntry(ticketId, selectedEntry);
    }
}
```
- **Where the range check runs.** It is reached from `settleWinningTicket` (`L304-L306` → `L533` → `L538`) and from unsettled redemption (`L314-L315`).
- **Settled redemption.** Here the binding is `ticketId == winningTicketId` (`L316-L317`). `winningTicketId` is written only at `L552`, after the `L538` check.
- **Refund amounts.** The caller never supplies an amount. It is the stored ranges (`L362-L363`) times the constant `ENTRY_PRICE` (`L367`; `L44`, which takes its value from `RaffleConstants.sol:L21`). `_ticketRanges` is written only at `L232`.

**The fee is read at execution, not quoted.**

```solidity
// Raffle.sol:L249-L250, L257-L258
uint256 quotedFee = getVrfRequestPrice();
if (msg.value < quotedFee) revert InsufficientVrfFee(quotedFee, msg.value);
...
(requestId, paidPrice) = requestRandomnessPayInNative(callbackGasLimit, requestConfirmations, 1, extraArgs);
if (paidPrice > msg.value) revert InsufficientVrfFee(paidPrice, msg.value);
```
- **The price is read live.** `L437` calls the wrapper's `calculateRequestPriceNative` live. The base contract reprices again at payment (`VRFV2PlusWrapperConsumerBase.sol:L82`) and pays exactly that amount (`L84`).
- **`msg.value` is only a cap.** Any excess goes back to the caller (`L262-L270`). The NatSpec says the same: `IRaffle.sol:L360`, "the value may change before request inclusion."

**Lifecycle and timing gates** read storage and `block.timestamp` inside the executing function. Each one is listed under Paths walked below.

**Rereads after an external call.** After each transfer the token contract is queried again rather than trusting the transfer's success: `Raffle.sol:L334-L337` (winner NFT), `L404-L405` (sponsor prize), and `RaffleFactory.sol:L127-L134` (escrow `ownerOf`, then `IRaffle(raffle).status()`).

**Registry reads are live.** `_isProtocolDestination` (`L593-L605`) calls `canonicalFactory.raffleImplementation()` and `canonicalFactory.isRaffle(destination)` every time it runs. It is called from `initialize` (`L187-L195`), from every mint and transfer through `_update` (`L498`), and from every quote payout through `_transferQuote` (`L565`).

**How the verdict was reached:** The verdict is `implemented`, limited to the on-chain half that the Holds-if marks as checkable here. Every external entry point decides from its own execution: storage, `block.timestamp`, a live `ownerOf`, and live external reads. No function trusts a caller's claim about state, and none reuses an ownership value or a price recorded earlier.

Why not the adjacent verdicts:
- **Not `partial`.** That verdict needs a path where the requirement fails. The client half is unexamined because no client code exists, which is not the same as failing.
- **Not `undecidable`.** The sentence could be checked against a client implementation, and the Holds-if gives a concrete on-chain test.
- **Not `stronger-than-spec`.** The `ownerOf` rereads after transfers (L335, L405, Factory L129-L134) go beyond this requirement. They are documented, though (`IRaffle.sol:L299-L301`, `IRaffleFactory.sol:L93-L97`), and they belong to the delivery and escrow requirements.

Confidence is medium rather than high. The on-chain half was read on every path, but the sentence's main subject, how clients build transactions, has no code in the provided tree.

**Open questions:**
- **The client half is unchecked.** Suppose a client builds `settleWinningTicket`, `redeemWinningTicket` or `refundTickets` from discovery data without rereading, for example by treating `TicketPurchased.recipient` as the owner. On-chain, the transaction reverts (L583, L317, L321, L360) instead of paying the wrong party, because the contracts re-verify. Any consequence beyond a failed transaction depends on client code that is not in scope.
- **"Current" is undefined.** DESIGN.md does not say what "current chain state" means for a client read: the latest, safe, or finalized block. The documents do not settle it.
