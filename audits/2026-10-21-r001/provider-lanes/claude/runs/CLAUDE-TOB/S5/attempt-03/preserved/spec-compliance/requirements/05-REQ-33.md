## REQ-33 — winner redemption requires the current ticket owner

> "redemption requires current ticket owner"
> — DESIGN.md line 2, sentence 13. Full sentence: "Settlement is permissionless, storage-only; redemption requires current ticket owner, burns claim atomically, and must revert all effects on delivery failure."

**Verdict:** implemented · confidence: high

---

**What this demands of an implementation:** Every path that delivers the winner's prize must revert unless `msg.sender == ownerOf(t)`. Here the prize is the escrowed NFT under `NftWon` or `winnerProceeds` under `CashWon`, and `t` is the winning ticket. Ownership must be read live in the same execution, not cached from settlement or an earlier owner. Three things have to hold together:
1. The comparison is against `msg.sender` itself, not "owner or approved". This is the strict reading.
2. The `ticketId` whose owner is checked is bound to the winning ticket. Otherwise a caller could pass a ticket they own.
3. No other function delivers the winner's prize around the check.

---

**Where enforcement lives:**

```solidity
// packages/contracts/src/Raffle.sol:L309-L325
function redeemWinningTicket(uint256 ticketId) external override nonReentrant returns (uint256 cashAmount) {
    if (winnerRedeemed) revert WinningTicketAlreadyRedeemed();
    Status result = status;
    if (result != Status.NftWon && result != Status.CashWon) revert InvalidStatus(result);

    if (!settlementComplete) {
        _settleWinningTicket(ticketId);
    } else if (ticketId != winningTicketId) {
        revert WinningTicketMismatch(ticketId, winningTicketId);
    }

    address winner = ownerOf(ticketId);
    if (msg.sender != winner) revert NotTicketOwner(ticketId, msg.sender, winner);

    winnerRecipient = winner;
    winnerRedeemed = true;
    _burn(ticketId);
```

- **The comparison (L320-L321).** Raffle does not override `ownerOf` or `_ownerOf` (no such definition in `src`). The call resolves to OZ v5.6.0 (`ERC721.sol:L2`): `ownerOf` → `_requireOwned` → `_owners[tokenId]` (`ERC721.sol:L61-L63`, `L426-L432`, `L146-L148`). For a burned or never-minted ID it reverts `ERC721NonexistentToken`. L321 compares against raw `msg.sender`. No `_isAuthorized`, `getApproved` or `isApprovedForAll` is consulted, so an approved operator, a prior owner, or an arbitrary caller reverts `NotTicketOwner`. There is no ERC-2771 or forwarder context that could substitute a different sender (0 hits in `src`).
- **L321 is the only gate.** `_burn` performs no authorization. `ERC721.sol:L295` says "This is an internal function that does not check if the sender is authorized to operate on the token." At `L304` it passes `auth = address(0)`, which skips `_checkAuthorized` (`L220-L222`). Raffle's `_update` override (`Raffle.sol:L497-L502`) only checks for protocol sinks when `to` is non-zero, and a burn does not reach that check. Remove L321 and nothing downstream stops a non-owner.
- **The ticket is bound to the winning ticket.**
  - Unsettled path: L315 → `_settleWinningTicket` → `_requireWinningTicket(ticketId)` (`L538`, `L579-L585`) reverts unless the ticket's stored range contains `winningEntry`. Unminted IDs have range `(0,0)`, and `winningEntry` is at least 1 (`L518`: `% totalEntries + 1`), so they fail.
  - Settled path: L316-L317 require `ticketId == winningTicketId`. `winningTicketId` is written only at `L552`, after the same range check at `L538`, and settlement runs once (`L534`).
- **Ownership is read at execution time, not cached.** No external call happens between entry (L309) and the burn (L325). `_settleWinningTicket` (`L533-L558`) does storage reads and writes, calls `ticketRange` (a view, `L451-L455`) and `Math.mulDiv` (`internal pure`, `Math.sol:L206`), and emits an event. So ownership cannot change between the read at L320 and the burn at L325. Settlement records no owner: `L528-L530` says it allocates "without transferring an asset or reading ticket ownership", and `L533-L558` contains no `ownerOf`. `winnerRecipient` is written only at L323, after the check.
- **The recipient is the owner.** Delivery pays `winner` (`L334` for the NFT, `L342` for cash). After L321 that address is also `msg.sender`, so the looser reading ("current owner is the recipient") holds as well.

**Other routes to the winner's prize** (checked to confirm the gate cannot be bypassed):
- Prize NFT outflows are L334 (this function) and L404. L404 is `releaseSponsorPrize`, which pays `sponsorRecipient` and is allowed only in `CashWon`/`Refunding` (L397). Under `NftWon`, the NFT can leave only through L334. ✓
- `winnerProceeds` is paid out only at L339-L342. Its only writes are L341 (zeroing) and L548 (allocation). ✓
- `NftWon`/`CashWon` are terminal. The status writes are L165 (constructor), L205 (`initialize`), L252 (gated to `Active` at L241), L299 (gated to `Active`/`Drawing` at L279/L289), L428 (gated to `AwaitingPrize` at L422) and L521 (gated to `Drawing` at L511). None leaves a won state, so `refundTickets` (`Refunding` only, L350) can never burn and pay out the winning ticket. ✓
- Inherited entry points: the Chainlink base has one external state-changing function, `rawFulfillRandomWords` (`VRFV2PlusWrapperConsumerBase.sol:L101-L107`). Only the wrapper can call it, and it calls `fulfillRandomWords` (`Raffle.sol:L509-L524`), which moves no assets. `RaffleFactory` never calls a raffle's redemption. Its only calls into a raffle are `initialize` (`RaffleFactory.sol:L109-L121`) and `status()` (`L132`). ✓
- Operator two-step: an approved operator can `transferFrom` the ticket to itself (`ERC721.sol:L115-L125`), because tickets stay transferable in every state (`Raffle.sol:L491-L502`). It then becomes the current owner. A redemption after that meets the requirement as written (`msg.sender` is `ownerOf` at execution time), so this is not a bypass. ✓

**How the verdict was reached:** `implemented`, not `partial`: all four paths that reach a delivery (L334 or L342) pass through L320-L321, and no other function delivers the winner's prize. Not `stronger-than-spec`: the Holds-if baseline is "reverts unless msg.sender is ownerOf(winning ticket) at execution time", and that is exactly the check. Under the looser reading, where the owner only has to be the recipient, the code is stricter, because operators cannot trigger redemption for the owner. But NatSpec documents the stricter rule: `IRaffle.sol:L270` says "Raised when the caller is not the current owner of the supplied ticket." and `IRaffle.sol:L333` says "Lets the current winning-ticket owner atomically burn the ticket and receive the NFT or cash prize." So the stricter rule is not an undocumented constraint.
