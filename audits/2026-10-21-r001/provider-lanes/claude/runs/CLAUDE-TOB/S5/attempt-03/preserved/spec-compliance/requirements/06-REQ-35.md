## REQ-35 — Winner redemption reverts every effect when delivery fails

> "must revert all effects on delivery failure"
> — DESIGN.md line 2, sentence 13

Full sentence: "Settlement is permissionless, storage-only; redemption requires current ticket owner, burns claim
atomically, and must revert all effects on delivery failure."

NatSpec says the same thing at `IRaffle.sol:L334-L335`: "If necessary, this first settles the supplied winning
ticket so the owner can complete both steps in one transaction. Any failed delivery reverts the burn and every
redemption state change."

---

**Verdict:** implemented · confidence: high

---

**What this demands of an implementation:** In `redeemWinningTicket`, every state write made before or during
delivery has to roll back when delivery of the NFT or USDC to the winner fails. That covers the in-call settlement
(`settlementComplete`, `winningTicketId`, `unsettledPot`, `sponsorProceeds`, `protocolFees`, `winnerProceeds`), plus
`winnerRecipient`, `winnerRedeemed`, the ticket burn, and either `prizeClaimed = true` or `winnerProceeds = 0`. The
task's holds-if names three failure modes: the callee reverts, it returns false, or ownership is wrong after the
transfer. So two things have to be true:
(a) each failure mode becomes a revert of the redeem call frame;
(b) nothing on the path catches that revert or ignores a failure signal. That means no try/catch, no low-level call
whose result goes unchecked, and no early `return` after effects have been written.

- **NFT, callee reverts:** L334 is a high-level external call and nothing wraps it, so a revert inside the prize
  contract propagates and the whole redemption reverts.
- **NFT, ownership wrong after transfer:** L335 reads `ownerOf` back from the prize contract and L336 reverts if
  the owner is not `winner`.
- **NFT, false return:** `IERC721.transferFrom` is declared with no return value (`IERC721.sol:L91`), so the call at
  L334 never decodes a returned `false`. Two cases follow:
  - The false return comes with no transfer. L335 catches it and the call reverts.
  - The false return comes with a completed transfer. The token has reached the winner, so delivery did not fail.
    See Open questions.
- **USDC, callee reverts:** `_transferQuote` (L342 → L566) calls `safeTransfer` with `bubble = true`, and
  SafeERC20 L189-L192 re-raises the revert.
- **USDC, false return:** `success` becomes false at L196 because `returndatasize() != 0`, and L34-L35 then reverts
  with `SafeERC20FailedOperation`.
- **USDC, empty return from an address with no code:** also false at L196, so it reverts the same way.
- **USDC balance after transfer:** there is no balance check. That matches the documented trust model, which says
  "Quote token and Chainlink wrapper are trusted canonical dependencies" (DESIGN.md L2) and "standard, non-rebasing,
  fee-free transfer semantics" (`Raffle.sol:L560-L561`). The holds-if's "post-transfer ownership mismatch" applies to
  the NFT only.
- **Rollback:**
  - Every write listed under "What this demands" happens in the same call frame as the delivery call:
    settlement writes at L548 and L551-L555 (reached through L315), then L323, L324, the burn at L325, L331 and L341.
  - A revert at L334, L336 or L342 therefore unwinds all of them, along with the `WinningTicketSettled` event (L557).
    This is EVM revert semantics, not a check in the code.
  - Raffle.sol contains no try/catch (see Searched).
- **Clone delegation keeps the revert:** each raffle is created with `Clones.clone` (`RaffleFactory.sol:L106`). The
  ERC-1167 runtime it writes (`Clones.sol:L56`, `...5af43d82803e903d91602b57fd5bf3`) does
  `DELEGATECALL … PUSH1 0x2b JUMPI REVERT JUMPDEST RETURN`. A failed delegatecall therefore REVERTs with the
  implementation's returndata, and the revert reaches the clone's caller.
- **Callers cannot create partial success:** a caller that wraps `redeemWinningTicket` in its own try/catch still
  sees the raffle's reverted frame rolled back (EVM semantics). No caller of any kind can produce a partially applied
  redemption.

---

**How the verdict was reached:** The verdict is `implemented` rather than `partial` because all four entry paths
(`NftWon`/`CashWon`, each with settlement pending or already done) behave the same way. On each, every effect sits in
the same frame as a delivery call, and every listed failure mode of that call becomes a revert: L334 propagation, the
L335-L336 ownership check, and SafeERC20 L34-L35/L189-L196. Nothing on any path turns a failure into a successful
return.

It is not `contradicted`, because there is no try/catch, no unchecked low-level call and no early return on the path.

It is not `stronger-than-spec`, because the post-transfer ownership read is one of the conditions the requirement
itself names, not an extra constraint.

**Open questions:**
- **The ownership check trusts the prize contract's own `ownerOf` (L335).** A hostile prize contract could make
  `transferFrom` do nothing while `ownerOf` reports the winner, and redemption would complete without delivering.
  No on-chain check in scope can detect that. The documents disagree on whether such a contract is in scope:
  DESIGN.md L2 says "arbitrary prize contracts and ticket recipients are untrusted", while `IRaffle.sol:L14-L15`
  says "Supported prizes are honest, standards-compliant ERC-721s." This is a trust-model question, not a gap in
  the revert-on-failure property, and is not counted against REQ-35.
- **A `false` from the NFT's `transferFrom` is ignored when the token actually moved** (no return value is decoded,
  per `IERC721.sol:L91`). That is consistent with EIP-721, which gives `transferFrom` no return value. It does not
  match a literal reading of "false return" applied to the NFT branch.
- **Scope:** the holds-if limits this requirement to delivery to the winner. If "redemption" is read more broadly to
  include refunds, `refundTickets` (L349-L372) has the same structure: burns at L364, a checked liability decrement
  at L368, then `_transferQuote` at L369, with no catch. The verdict would not change.
